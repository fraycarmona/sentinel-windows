# Auditoría de evasión de SENTINEL 0.4

Fecha: 2026-11-13. Auditoría interna de código y configuración, con pruebas de resolución DNS no destructivas. No es una certificación ni una auditoría independiente. Base del repositorio: 18e5b81ed55fbf3e6d4e61baa9915e9e5f814221.

## Resultado

**El filtro DNS funciona, pero actualmente SENTINEL no impide que un usuario decidido eluda el bloqueo.** Hay una evasión de resolución demostrada mediante HTTPS externo, además de varias limitaciones de arquitectura. La espera de 24 horas regula los flujos normales de retirada; no restringe todas las formas de debilitar el filtro ni constituye protección contra un administrador.

No se cambió DNS, no se detuvo el servicio, no se instaló VPN ni se abrieron sitios adultos reales durante esta auditoría. Las únicas consultas de prueba fueron Twitter y el dominio oficial de diagnóstico del proveedor. Una respuesta DNS externa demuestra que se evita el resolvedor local, no demuestra por sí sola la carga de una página adulta concreta.

## Detalles que afectan a la espera

`remove-lab.ps1` y `strict-lab.ps1` comprueban Ready para la retirada normal. Sus opciones de emergencia administrativas omiten esa espera deliberadamente. Además, `repair-service.ps1` restaura DNS antes de reemplazar el motor, usando recuperación; si falla después, puede dejar Internet disponible sin filtro. Por tanto, la restricción de 24 horas no cubre todos los flujos que reducen la protección. Hay que modelar reparación, actualización y recuperación como operaciones diferentes, con permisos y estados explícitos.

Los permisos leídos mediante SCM conceden control completo al grupo Administradores y no conceden parada a los grupos interactivos/servicios consultados. Esto no demuestra permisos de todas las cuentas o procesos: sí confirma que el administrador conserva el control. [Modelo de seguridad de servicios Windows](https://learn.microsoft.com/en-us/windows/win32/services/service-security-and-access-rights).

No se debe intentar resolver esto ocultando el programa, impidiendo la recuperación del sistema o cambiando UAC/Defender. El objetivo realista debe ser resistencia a evasiones habituales desde una cuenta estándar.

## Recuperación abierta y posible denegación de servicio

`Engine.cs` comparte un límite de 64 solicitudes entre TCP y UDP. Las conexiones TCP admitidas pueden ocupar una plaza durante hasta 10 s; cuando no hay plazas se descartan otras solicitudes. No hay cuota por cliente ni reserva para las consultas de salud. Una carga local sostenida podría impedir responder a `example.com` y hacer que el guardián restaure el DNS. **Es una hipótesis respaldada por código, no un ataque ejecutado sobre el PC.** La corrección del error 10054 elimina el fallo anterior, pero no demuestra resistencia a saturación.

La recuperación abierta se añadió para reparar un corte real de Internet. Es un intercambio entre disponibilidad y restricción, no un mecanismo anti-evasión. No activar un corte permanente de red como supuesto arreglo sin diseñar y probar la recuperación.

## Navegación privada y contenido mixto

Incógnito por sí solo no evita el DNS de Windows si usa el mismo resolvedor. Actualmente no está deshabilitado y puede coincidir con un navegador/perfil que utilice otra ruta de resolución. No confundir esas dos causas.

El proveedor filtra categorías de dominios; no inspecciona cada publicación. Buscadores, servicios de mensajería, redes sociales, almacenamiento compartido y páginas proxy pueden servir contenido bajo nombres permitidos. No se verificó aquí contenido adulto en ninguna plataforma. Fuente del alcance por dominio: [Cloudflare Families](https://developers.cloudflare.com/1.1.1.1/setup/).

## Orden de trabajo recomendado

1. Definir formalmente el objetivo: cuenta estándar, navegadores compatibles y recuperación administrativa. Separar indicador DNS de cobertura anti-evasión y avisar claramente cuando el guardián retira el filtro.
2. Validar y activar las políticas por navegador con pruebas benignas de DNS, proxy, incógnito e invitado. Para Comet, comprobar políticas reales; no atribuirle automáticamente las de Chrome.
3. Añadir control de salida y de aplicaciones sin romper Windows: DNS externo, DoT/DoQ, aplicaciones no aprobadas y extensiones. HTTPS arbitrario sigue siendo una limitación que debe declararse.
4. Diseñar recuperación filtrada y resistencia a saturación; proteger configuración con SID propio. Probar esta capa fuera del PC de uso diario antes de aplicarla.
5. Autenticar IPC y actualizaciones. Ensayar adaptadores nuevos, suspensión, reinicio, pérdida de proveedor y restauración, incluyendo usuarios distintos.

Ningún hallazgo se considera corregido por este informe. El filtro existente se mantuvo activo durante la auditoría. No se asegura exhaustividad: quedan sin probar túneles reales, aplicaciones concretas, ataques de carga, arranque alternativo y manipulación administrativa del sistema.
